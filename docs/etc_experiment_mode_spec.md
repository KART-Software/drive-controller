# ETC 同定実験モード 仕様書 (ドラフト)

Status: **仕様確定 (Q1–Q18 全決定, 2026-08-13) — 実装 GO 待ち**。
関連: [etc_control_improvement_plan.md](etc_control_improvement_plan.md) §6 (実験計画)

## 1. 目的とスコープ

ベンチ上で ETC の同定実験 3 種 (ポイント滞在 / リリース / 中間ステップ) を
**console からワンボタンで全パターン自動実行**するファーム内実験モードを追加する。
データは既存の SD ログ (1 kHz) に記録し、PC でフィットする。

スコープ外: フィット処理 (PC 側)、FF 制御の実装、起動時ヘルスチェック
(将来ポイント滞在のコードを縮小再利用する)。

## 2. 確定要件 (ユーザー指定)

| 実験 | パターン |
|---|---|
| ポイント滞在 | **−5〜105% を 1% 刻み** (111 点) |
| リリース | **−5〜105% の 1% 刻み**の各点からリリース (111 点) |
| 中間ステップ | **0〜100% の 10% 刻み 11 点 × 11 点から from==to を除いた 110 パターン** (Q6 決定) |

- console に**実験ごとの開始ボタン** + ワンボタンで全パターン自動実行
- 前提: 拡張ストッパー −15/115%、ソフトガード ±(−10/110)%
- ストッパー非接触ポリシー・エンジン停止中のみ (計画書 §6)

## 3. シーケンス仕様

### 3.1 ポイント滞在 (POINT_DWELL)

```
上り: -5, -4, ..., 104, 105        (111 点)
下り: 104, 103, ..., -4, -5        (110 点)   計 221 点
各点: [静止待ち] → [記録窓 RECORD_HOLD_MS] → 次の点
```

- 上り→下りの両方向で摩擦ヒステリシス (幅 2·Tc) を取る。
- 目標は manual target への絶対値セット。PID が追従・保持する。
- **静止判定 (Q1 決定)**: 直近 `STATIONARY_WINDOW_MS` の窓で
  `|Δtps| < STATIONARY_TP_TOL` **かつ** `|Δduty| < STATIONARY_DUTY_TOL`。
  θ だけでなく u も見る理由: 摩擦帯で θ が目標手前に張り付いている間は
  I 項が積分を続け u がランプしている (stick-slip の途中) — その瞬間の
  記録は保持 duty を汚染する。u も静止 = I が積み終わった真の平衡。
- 目標 ±許容誤差への到達は**要求しない**。静止すればその点は有効
  (マップは目標値ではなく実測 θ と平均 duty・平均電流で組む。摩擦で
  目標手前に止まってもそのまま 1 点として使える)。
- 静止後の記録窓 (固定 1000 ms) の平均 duty・平均電流が FF マップの 1 点。

### 3.2 リリース (RELEASE)

```
各点 (昇順 -5..105):
  [静止待ち] → [保持 RELEASE_HOLD_MS] → [コースト: バネ戻りが静止するまで] → 次の点
```

- コースト = ETC 停止 (SLP=LOW、モーター電源リレー OFF)。バネ戻り軌道が
  純機械系データになる (電流 ≈ 0)。
- **コースト終了 = 静止判定 (Q4 決定)**: §3.4 の共通判定器を再利用
  (コースト中は u=0 なので実質 θ の不動判定)。バネ休止位置での静止を検出
  したら再アーム (既存 `startEtc()` = `pid.reset()` 込み) して次の点へ。
  戻り時間のリリース高さ依存に自動適応し、専用の固定時間パラメータは持たない。
  タイムアウト 8 s も共通 (成立しなくても次へ進む)。
- バネ休止位置 (−15% 付近) を通るのは正常挙動。

### 3.3 中間ステップ (STEP)

```
各ペア (from, to) = (10i, 10j), i,j = 0..10, i ≠ j  (計 110 ペア):
  [静止待ち@from] → 目標を to へ瞬時切替 → [静止待ち@to] → 次のペア
```

- ペア順序: from 昇順 → to 昇順、from==to は除外 (Q6 決定)。
  `exp_index` は除外後の連番 0–109。
- 固定保持は持たない (Q7 決定): 静止判定の窓 (500 ms) がステップ前後の
  静的セグメントを兼ねる。
- 2 ゲインセット検証 (計画書 §6) は手動 2 周 (Q8 決定):
  A = (3.0, 0.4, 0) で実行 → `SetEtcPidCmd` で B = (6.0, 0.4, 0) に変更 →
  再実行。実験前に anti-windup 導入が前提。

### 3.4 タイミングパラメータ (提案値 — 要承認)

静止判定 (全実験共通の判定器。Q1 で決定):

| 定数 | 提案値 | 意味 |
|---|---|---|
| `STATIONARY_TP_TOL` | 0.2 % | 窓内の TPS 変動幅 \|Δtps\| 上限 |
| `STATIONARY_DUTY_TOL` | 0.5 % | 窓内の duty 変動幅 \|Δduty\| 上限 (I 項ランプ検出) |
| `STATIONARY_WINDOW_MS` | 500 ms | 判定窓 |
| `SETTLE_TIMEOUT_MS` | 8000 ms | 静止しない場合のタイムアウト (黙って次フェーズへ進む, Q3) |

フェーズ時間:

| 定数 | 提案値 | 意味 |
|---|---|---|
| `RECORD_HOLD_MS` | 1000 ms | ポイント滞在の記録窓 (静止後。平均 duty/電流の算出区間) |
| `RELEASE_HOLD_MS` | 1000 ms | リリース前の静止保持 |

コースト終了は固定時間ではなく静止判定の再利用 (Q4 決定。§3.2)。
ステップの前後保持も静止判定のみで固定時間なし (Q7 決定。§3.3)。

### 3.5 所要時間見積り

| 実験 | 概算 |
|---|---|
| ポイント滞在 221 点 × ~2 s (静止待ちは 1% 移動なので速い) | **約 8 分** |
| リリース 111 点 × ~3 s | **約 6 分** |
| ステップ 110 ペア × ~3.5 s | **約 7 分** (×2 ゲインセット手動 2 周で約 14 分) |

SD ログは 1 kHz × 132 B ≈ 132 KB/s → 全実験でも数百 MB 未満。

## 4. アーキテクチャ

新クラス **`etc::ExperimentRunner`** (`src/etc/experiment_runner.{hpp,cpp}`)。
`loop()` から毎イテレーション `tick(now)` される FSM (autoShifter と同じパターン)。

設計原則:

1. **目標注入は EtcTarget の manual モード経由** (`setManualTarget(double)` を
   新設、既存 `MANUAL_MIN/MAX = −10/110` にクランプ)。PID・モーター経路は
   通常運用と完全に同一 =「使う構成のまま測る」。
2. **コーストは SHUTDOWN アーミング層を経由**。runner は `wantsCoast()` を
   立てるだけで、main.cpp のアーミング判定に④として追加:
   ```
   ① plausibility ラッチ → RELAY=LOW + stopEtc   (最優先, 不変)
   ② SIG_IN=LOW / ③ MOTOR_OFF → stopEtc          (不変)
   ④ experimentRunner.wantsCoast() → stopEtc      (新設)
   else → startEtc
   ```
   ①〜③が常にコーストより優先。既存の安全順位を崩さない。
3. シーケンス定義 (点列・ペア列) はファーム内に焼き込み。proto は type のみ。

### 4.1 状態機械

```
Idle ──start()──> Settling ──整定/timeout──> Holding ──┬─(Dwell/Step完)──> 次indexへ (Settling)
 ^                                                     ├─(Step前半)──> to へ切替 (Settling)
 │                                                     └─(Release)──> Coasting ──COAST終了──> 次indexへ
 └──── stop() / ガード違反 / 全 index 完走 ────────────────────────────────┘
```

状態: `Idle / Settling / Holding / Coasting`。index + (Step のみ) from/to フラグ。

## 5. 開始条件 (start が拒否する条件)

| 条件 | 判定 |
|---|---|
| モードノブ ≠ MOTOR_OFF | MOTOR_OFF はアーミング③が ETC を止めるため実験が進行不能。それ以外の位置なら可 (Q11 決定: ノブによる実験許可は要求しない — console 接続時は走行時ではない) |
| エンジン停止 | engine パルス ≈ 0 Hz |
| 車両静止 | 車輪速 4 輪 ≈ 0 Hz |
| plausibility 正常 | `currentlyValid()` かつ ① 未ラッチ (`validLatched()`) |
| ETC 稼働中 | SIG_IN=HIGH (②) かつモーター ON。止まったまま開始すると TPS が休止位置で「静止」と判定され、無意味なデータで完走する (2026-10-06 修正) |
| SD ログ動作中 | `sensorLogger.active()` — 記録できない実験は無意味 (Q13 決定) |
| 実験非実行中 | 二重開始拒否 |

拒否時は `ok=false` 応答 + 理由を debug 送信。

## 6. 実行中ガード (毎 tick、違反で中断)

| ガード | 内容 |
|---|---|
| ノブ MOTOR_OFF | MOTOR_OFF 位置になったら中断 (アーミング③で ETC が止まり進行不能のため)。他位置への移動は不問 (Q11 決定) |
| エンジン始動 | engine パルス > 0 で中断 |
| plausibility | `currentlyValid()` false または ① ラッチで中断 |
| SIG_IN | LOW になったら中断 (アーミング②で ETC が止まり進行不能) |
| ETC 停止 | コースト区間以外でモーター OFF なら中断 (`ETC not armed`) |
| TPS 上限 | tps1 > **110%** で中断 |
| TPS 下限 | tps1 < **−10%** で中断。**ただし RELEASE 中は不適用** (バネ休止 −15% を通るのが正常。モーターは切れており押し付けは物理的に起きない) |
| ストール | \|u\| > `STALL_DUTY` かつ \|tps − target\| > 2% かつ TPS が `STALL_MS` 動かない → 中断。※「目標付近で高 duty 保持」は正常動作 (高開度はバネで保持 duty が高い) なので target 乖離条件を必ず含める (Q14) |

中断 = `stop()`: manual 解除 → 通常のモード別ターゲットへ復帰、理由を debug 送信。

## 7. プラウシビリティとの整合

- **target-vs-TPS チェック** (乖離 10%×1s で復帰不可ラッチ): コースト・大ステップで
  必ず乖離するため、**実験中のみ `PlausibilityValidator::suspendTargetCheck(true)` で一時停止**し、
  `stop()` で再開する。一時停止は config 由来の `targetCheckFlag` とは独立。
  - **フラグを退避・復元する方式は使わないこと** (旧実装)。実験中に `set_config` / Revert /
    `set_plausibility_flags` が来るとフラグが書き戻されてコーストで ① がラッチし、終了時には古い値で
    上書きしていた (2026-10-06 修正)。
  - 再開時は「最後に正常だった時刻」をリセットする (停止中の乖離を持ち越して即ラッチしないため)。
  - 一時停止中は判定自体を呼ばない (呼ぶと `ERR_APPS_TPS_TARGET_FAILURE` が立って消えない)。
- **回路チェック (断線検出) は有効のまま**。`TPS_MARGIN=15` により −15〜115% は
  正常扱いなので、±(−10/110) ガードが必ず先に効き誤ラッチしない。
- APPS 系チェックも有効のまま (ベンチではペダル不使用で常時整合)。

## 9. データ記録

### 9.1 SD ログ拡張 (LogRecord v2 → v3, 128 → 136 B)

| 追加フィールド | 型 | 内容 |
|---|---|---|
| `exp_type` | u8 | 0=none, 1=dwell, 2=release, 3=step |
| `exp_index` | u8 | シーケンス内インデックス (dwell 0–220 / release 0–110 / step 0–109) |
| `exp_phase` | u8 | 0=idle, 1=settling, 2=holding, 3=coasting |
| `duty` | f32 | モーター PID 出力 u [%] (`MotorController` に getter 追加) |
| `vbat` | f32 | バッテリー電圧 [V]。**CAN 受信 (30 Hz) の最新値** (Q12 決定)。メッセージ定義が kart-can に入るまでは 0 |

- 既存 `_pad[3]` を置換 + 8 B 拡張。`SENSOR_LOG_VERSION=3`、`decode_log.py` 対応。
- **モーター電流は既に `adc[4]`** (`MOTOR_CURRENT_CH`, ~20 mV/A + 50 mV offset) に
  生値で記録されている — 追加不要。
- `target_tp` 列が manual target を含むため、PC 側は (exp_index, exp_phase,
  target_tp) でセグメント切り出しが自動化できる。
- **Vbat は CAN で受信予定 (30 Hz)** (Q12 決定)。前提: kart-can 側のメッセージ
  定義 (frame ID・スケーリング・送信ノード) の確定。定義され次第 `CanRxData`
  に受信を追加しログへ。30 Hz → 1 kHz レコードには最新値ホールドで埋める
  (電圧は遅い量なので十分)。
- duty getter の ISR/loop 間共有: float の 32bit ストアは Cortex-M7 でアトミック
  なので `volatile float` で保護不要。
- **duty 列の不変条件 = 常に実印加値**: モーター停止中は ISR が止まり getter 値が
  凍結するため、`setMotorOff()` で記録値を 0 にクリアする。これによりコースト中の
  duty 列は正しく 0 になり、リリース軌道のフィットが u=0 を仮定せずログを
  そのまま入力にできる。

### 9.2 進捗通知

`sendDebugf` で開始 / 10 点毎の進捗 / 完了 (タイムアウト件数付き) / 中断理由を
送信 (console の既存 debug 表示で見える)。静止タイムアウトの点毎警告は出さない
(Q3 決定: 非静止データも有効。分類は PC 側)。専用テレメトリは初版では作らない (Q9)。
